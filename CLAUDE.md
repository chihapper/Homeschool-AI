# Homeschool-AI — project guide for Claude Code

A Socratic AI tutor for homeschool families. Multi-agent TypeScript app: a Fastify server hosts the
agents and the browser voice socket; a Vite/React app is the parent/student UI.

## Layout

- `apps/server/src/domain/types.ts` — every persisted object and structured LLM output, as Zod schemas. Change schemas here first.
- `apps/server/src/agents/` — one file per agent (`curriculum`, `profiler`, which runs the general intake, `course-intake`, which asks what a student already knows about a course, `tutor`, `assessor`, `reference`, which checks one outside fact against Wikipedia, and `profile`, which revises the learner's two records after each report) plus `base.ts` (prompt assembly + streaming tool loop) and `pronouns.ts` (a record must not give a child a gender nobody stated).
- `apps/server/src/orchestrator/session.ts` — deterministic state machine; the only place phase transitions and persistence happen. It also plans a sitting (general intake, course intake, lesson), hands one session over to the next, and writes an intake's record in the background. `orchestrator/outside.ts` records outside facts the reflect pass flags and runs their checks as background jobs.
- `apps/server/src/reference/wikipedia.ts` — Wikipedia through the free Action API: a User-Agent naming `WIKIPEDIA_CONTACT` (Wikimedia's rule; anonymous programs get 10 requests a minute), one request at a time, a day's cache, 429 retry-after honoured; and the article cut into summary, contents, ranked passages and sections for the checker.
- `apps/server/src/domain/focus.ts`, `domain/progress.ts`, `domain/profile.ts`, `domain/intake.ts`, `domain/told.ts` — pure: the parent's focus (what the tutor teaches), the cross-session progress view, what of a proposed revision of the two records lands (slow fields need two consecutive sessions to agree), with undo, the intakes' fixed parts (the passage and its three bands of questions, which concepts a course intake asks about, what a sitting consists of), and what the tutor has already told the learner. `ingest/pdf-text.ts` joins PDF text by glyph geometry (scans fuse words otherwise).
- `apps/server/src/voice/` — voice, in the browser: `live.ts` (WebSocket per session: mic audio in, spoken reply out, barge-in), `stt-assemblyai.ts` (streaming speech-to-text with end-of-turn detection), `tts-inworld.ts` (Inworld, the default) and `tts-elevenlabs.ts` (ElevenLabs), the text-to-speech adapters behind the `ttsProvider` setting (all deliver 24 kHz, read once per turn; Inworld voices a whole reply as one context on a socket opened at `mic_start`, ElevenLabs takes sentence batches), `sentence-chunker.ts`, `pcm.ts` (`Pcm16Stream` keeps a network stream in whole samples). Provider specifics stay in the adapters; the turn loop lives in `live.ts`.
- `apps/server/src/ingest/` — file -> text -> heading-aware chunks -> BM25 index. `extract.ts` dispatches on file type (pdf, docx, epub, odt, rtf, html, text, zip) and refuses anything else by name with the conversion to run; `documents.ts` holds the markup readers and the shared text helpers; `ocr.ts` reads page scans through the model. `ingest/media/` handles pptx, video (yt-dlp), podcasts (RSS), speech-to-text, and web pages; `media/sources.ts` is the single entry point.
- `skills/*/SKILL.md` — agent competencies, loaded at runtime into system prompts. Tune behaviour here before touching code. `initial-assessment` is the general intake and `course-intake` the course intake: each says how to hold the conversation and how to write its record.
- `apps/web/` — React UI (text mode works with only an Anthropic key; voice needs AssemblyAI plus Inworld or ElevenLabs). Tabs: Students (add a student and hold the general intake right there), Courses (material and focus; start or continue a student on a course), Lesson (the conversation; a first lesson on a course opens with the course intake), Reports, Settings. `components/Conversation.tsx` is the one live-conversation view the intake and the lesson both use; the page owns the session and the voice connection (`VoiceClient.prepare()` inside the click, so the browser allows audio), the component runs the turns.
- `data/` — file-backed JSON store (gitignored). One JSON per course/learner/session/report, and one per student per course in `course-knowledge/`. `store/migrate.ts` converts older records when a server or CLI starts (never on import) and keeps the originals in `data/backups/`.

## Conventions

- Claude API via `@anthropic-ai/sdk` only. Defaults `claude-opus-5-5` (offline agents) and `claude-sonnet-5-5` (live tutor); adaptive thinking on; effort from config, always set explicitly (Opus 5.5's own default is one step lower than Opus 5's). Never add `temperature`, `budget_tokens`, or a forced `tool_choice`. What each model accepts is one table in `llm/models.ts` (effort support; how thinking is turned off: `disabled` on Opus 5 / Sonnet 5, `between_tools` on Sonnet 5.5, never on Opus 5.5 and Fable, where low effort is the control) and `reasoningParams` in `llm/client.ts` reads it; nothing else in the app names a model. **To adopt a new model:** read its migration guide (platform.claude.com/docs/en/models/<model>/migration-guide, or `/claude-api migrate`), add its ID to `MODEL_OPTIONS`, add or adjust its row in `modelRules`, extend `models.test.ts`, and run the doctor ping plus one scripted session. IDs use hyphens, never dots (`claude-sonnet-5-5`); `normalizeModelId` repairs the dot, and `PUT /api/settings` checks a typed ID with the API before saving. `max_tokens` covers thinking as well as words, so caps leave room for it (`SPEAK_MAX_TOKENS` / `REFLECT_MAX_TOKENS` in `tutor-agent.ts`).
- Structured outputs use `client.messages.parse` + `zodOutputFormat`. Avoid JSON-schema features structured outputs reject (numeric min/max, defaults); validate those in code.
- Streaming agents use `client.beta.messages.stream` (needed for server-side refusal fallbacks). Always check `stop_reason` before trusting content.
- System prompts: stable role + skills first (cached), per-session context after. Keep the stable part byte-identical across turns.
- Agents *request* transitions through tools; the orchestrator validates and applies them. Don't let an agent mutate session state directly.
- A tutor turn is **two calls**: `tutorTurn` speaks (no bookkeeping tools, thinking off, the learner is waiting) and `reflectTurn` records observations, requests the phase change, and may name ONE thread for the next turn (`open_thread` -> `orchestrator/notes.ts`), all while the learner listens. Never move bookkeeping back into the speaking call, not even as words in a directive it reads (a retrieval directive that said "record the result" made it narrate aloud; that answer is filed by the reflect pass via `Session.retrievalConceptId`); never let the speaking call think. Once a spoken reply ends in its question, any tool call ends the turn (`streamTurn` in `agents/base.ts`). The speaking call gets the passages that match the learner's latest words before it speaks (`passagesForLatestReply`), so it rarely needs a lookup mid-reply, and it must never narrate one ("let me check the material" was spoken aloud on 2026-09-25). `respond()` returns the reflect pass as `reflection` and awaits any pending one before the next turn (`settleReflection`). The thread is not a competing instruction: it rides with the phase guidance in one block (phase = what kind of work this turn does, thread = what the work is on) and carries how many turns it has been open, so the tutor varies its angle at first and then asks plainly. Keep it that way; an earlier version made the note *outrank* the phase, which worked but read as an org chart rather than a dialogue. A fact the tutor stated is told, not recalled (2026-09-30: it read out "753 B.C.", six turns later asked the learner for the date, then denied having said it; replayed, Sonnet 5 denied in 10 of 16 tries). `domain/told.ts` finds the key-fact figures the tutor was the first to say, across every concept of the walk; the speaking call gets them inside its final instruction (as a block of their own they set off lookups after the reply), the reflect call as `<already_told>`. The reflect pass records what the tutor stated as kind `told`, which is never assessment evidence (`isEvidence`), and settles a learner's "you told me that" against the transcript in the thread instead of leaving it in dispute.
- Grounding is a product requirement: the tutor teaches only from the course material, and the assessor audits this. Keep it that way. The one exception is a fact the learner brings in ("Aphrodite saved Aeneas"), governed by the parent's `outsideKnowledge` setting, frozen on the session: the tutor may confirm, correct or say it is not sure, labelled as outside the material; it never brings in outside facts itself, never rules on faith or values, and the material wins where it differs. The reflect pass flags such facts (`flag_outside_claim`); the Wikipedia check runs as its own job, never inside the reflect pass the next turn waits on, and its verdict is merged at the start of the next turn, the only point where nothing else is writing the session. When the tutor owes the learner a follow-up (it said it was not sure, or the check contradicts it), the checker has already written the sentence (`sayToLearner`); the orchestrator speaks it at the start of the next reply (`SAY_FIRST` in `orchestrator/outside.ts`) and the speaking call carries on from it (`saidFirst`). Asked to open with a follow-up itself, the speaking model did so in about a third of live tries. Where the material tells it differently, the sentence gives the reading's version first and never calls it wrong. Faith and scripture never go to Wikipedia, whatever the wording (`aboutFaith`): a student's "historians doubt the census in Luke" once came back "Luke is in error" in a family's report. Every outside fact goes to the parent's report.
- A student has two records (2026-10-05, docs/INTAKE.md). The learner profile is how to work with them on any course: the general intake writes it. The course-knowledge record (`CourseKnowledge`, one per student per course) is what they know about one course: the course intake writes its starting points (an estimate per concept, their own words, how sure they said they were, and what the material says where they contradict it), which are a baseline and never rewritten. After every report the profile pass (`agents/profile-agent.ts`, skill `profile-update`) proposes a revision of both that `domain/profile.ts` lands or holds. The course notes (prior knowledge, gaps, course guidance) and the profile's fast fields (interests, demonstration preferences, guidance) change on one session's evidence; the profile's slow fields (pace, challenge tolerance, verbal level, depth) describe the child and move only when two consecutive sessions propose the same (`held` on the previous update). Every change is recorded with its reason, `previous` and `previousCourse`, and the parent can undo the latest, which puts both records back (`POST /api/learners/:id/profile/undo`). The pass runs in the background after `endSession` returns the report, one write at a time per learner, and reads both records again before saving. The parent decided apply-with-undo (2026-09-27) and may switch to propose-and-approve later, so keep landing and recording separate. `depth` is how much of an answer the learner is ready for, from what they demonstrate, never the mastery bar; the tutor and the reference checker read it (`studentLevel`). There is no learning-style field and none may be added: `intakePreferences` was dropped, the entry point of a concept follows what the student knows about it (its starting point, then the course notes), and what a student does when confused goes in the guidance, for the opening move only. `Learner.parentNotes` is the parent's own words: the tutor follows them as written and no pass rewrites them.
- The two intakes are sessions of their own (`Session.kind`), and a sitting is a chain of them: general intake, course intake, lesson (`planSitting` in `domain/intake.ts`; `createSession` starts the first, and each intake starts the next when it calls `finish_intake`). In the web app the general intake is held on the Students tab when a student is added (`only: "general-intake"`), and the Lesson tab starts every sitting with `skipGeneralIntake`, so a first lesson on a course opens with the course intake and the general intake never runs from there (the user's call, 2026-10-06). The general intake never uses the family's course: it reads the passage in `domain/intake.ts`, which the orchestrator speaks word for word when the agent calls `read_passage`, and its two questions come from three bands by grade, stepping up on a sound answer and down on a weak one. The course intake asks one first-step question per concept `selectProbeConcepts` chose (never a skipped concept, never one about faith: `aboutFaith`), with "how sure, 0 to 10?" in the same turn, and teaches and corrects nothing. An intake's record is written in the background (`writeIntakeRecord`), never before the reply: the hand-over line and the next session's opening are one reply (`RespondResult.handover`), so there is no dead air, and a message sent to a finished intake is answered by the session that took over (`Session.continuedIn`). While a record is on the way it is marked pending on the learner or the course record, the intake is not held again, and the lesson that follows reads the course intake's exchange itself (`intakeJustNow`). Both extractions are checked in code for a gender nobody stated (`agents/pronouns.ts`). `npm run personas:intake` plays three scripted students through both intakes on a running server and checks all of this.
- Scope is one unit at a time plus a parent's view; no scheduling, planning, or grading. Focus (what the tutor teaches) is the parent's decision on `Course.focus`, never an agent's. It is resolved once at `createSession` into `Session.conceptIds`; every read in a running session goes through `domain/focus.ts` (`walkedConceptIds`), never a live `lesson.conceptIds`, so a mid-session edit cannot change the walk or the cached prompt prefix.
- Latency is a product requirement for the live tutor: stream every delta, keep bookkeeping and thinking out of the speaking call, keep the cached prefix stable, gate effort/thinking params on the model (`reasoningParams`). Every assistant turn records `latency`; see `docs/LATENCY.md`.
- External binaries (`yt-dlp`, `whisper`) and STT APIs are optional and must fail with a clear message, never crash ingestion of other sources.
- An unreadable upload must never become text. `extract.ts` refuses a binary rather than reading it as UTF-8, because mojibake looks enough like prose that the curriculum agent will build a course from it. Every refusal names the conversion that produces a readable file.
- Tests are pure (no network, no binaries). `npm test` must pass before pushing.

## Commands

```
npm install
npm run dev:server            # http://localhost:3001
npm run dev:web               # http://localhost:5173
npm run ingest -- --title "Bio 7" ./chapter.pdf
npm run chat -- --learner "Maya" --course <courseId>
npm run personas:intake       # server running: three scripted students through both intakes, with checks
npm test && npm run typecheck
```
